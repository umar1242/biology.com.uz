# Смоук-тесты API

Два скрипта, которые прогоняют боевой API целиком — не моки, а живые
HTTP-запросы к запущенному серверу.

```bash
npm run test:api         # все три набора
npm run test:api:staff   # учительская часть
npm run test:api:student # ученическая часть
npm run test:api:cert    # сертификатный экзамен
```

Требуется: поднятая база, запущенный API и учётные записи-фикстуры. Последние
создаёт `E2E_SEED=yes npm run seed:e2e` — учителя `alice` / `bob`, помощник
`helper_carol` (пароль `secret1234`) и трое учеников. Раньше их приходилось
заводить руками, и на чистой базе набор был неработоспособен.

## Настройка окружения

Ничего не зашито в скрипты — всё решается в `test/lib.sh`:

| Переменная | Зачем | По умолчанию |
|---|---|---|
| `API_BASE` | адрес API | `http://localhost:3000/api/v1` |
| `DATABASE_URL` | прямое подключение к базе (так работает CI) | — |
| `PG_CONTAINER`, `PG_USER`, `PG_DB` | доступ через `docker exec`, если `DATABASE_URL` не задан | `myproject-postgres-1`, `postgres`, `course_platform` |
| `TELEGRAM_BOT_TOKEN` | подпись initData; иначе берётся из `apps/api/.env` | — |

Токен здесь — не доступ куда-либо: это ключ HMAC, которым подписывается
initData Мини-аппа. Он обязан совпадать с тем, что проверяет API, и только.
Поэтому в CI стоит заведомо поддельный, а проверка подписи всё равно
проверяется по-настоящему.

`test/telegram-stub.mjs` отвечает вместо Telegram: часть эндпоинтов ходит в
Bot API прямо внутри запроса (диплинку нужен `getMe`, записи на курс —
`createChatInviteLink`), и без ответа эти сценарии просто не выполнить.

## Что покрыто

**`e2e-staff.sh`** (99 проверок) — вход и оба вида отказа, курсы, модули,
уроки (live/recorded + валидация несовместимых полей), ДЗ, ученики, выдача и
отзыв доступа, штрафные баллы и блокировка, помощники и их права по курсам,
сводка дашборда, очередь проверки, настройки, удаление в правильном порядке.

**`e2e-student.sh`** (41 проверка) — вход по Telegram initData (включая
подделанную подпись), выдача своего курса, ДЗ и сдач, и — главное —
изоляция: посторонний ученик получает 404 на каждом ресурсе, а
заблокированный или отозванный доступ убирает курс из выдачи. Отдельно —
анкета как условие входа: без неё приложение отвечает 403 `not_onboarded`,
и открыты только два маршрута, ведущие к самой форме.

Скрипты создают свои данные и не трогают чужие, но пишут в ту же базу —
гоняйте их на dev-базе, а не на боевой.

## Как читать результат

Каждая строка — `ok` или `FAIL` с ожидаемым и фактическим HTTP-кодом; в конце
сводка `N passed, M failed` и список падений. Оба набора должны давать
`0 failed` — любое падение это регрессия.

Ученический набор сам создаёт себе курс/модуль/урок/ДЗ и выдаёт доступ, а по
выходе удаляет всё созданное, поэтому не зависит от того, что лежит в базе, и
не копит мусор между прогонами.

## e2e-cert-exam.sh — сертификатный экзамен

Прогоняет весь сценарий Milliy Sertifikat: учитель создаёт вариант →
прикрепляет файл → вводит ключ 1–35 → публикует; ученик решает, шлёт фото
по заданиям 36–43, сдаёт; учитель выставляет баллы; ученик видит результат.

```bash
API_BASE=http://127.0.0.1:8080/api/v1 bash test/e2e-cert-exam.sh
```

116 проверок (банк заданий, якори, карточка задания). Тест сам создаёт вариант и ученика и удаляет их за собой
(`trap cleanup EXIT`), поэтому его можно гонять на боевой базе.

Что именно проверяется помимо happy path:
- структура из спецификации: A–D для 1–32, A–F для 33–35, веса 30/35/10;
- публикация блокируется без файла и без полного ключа (409);
- ключ не утекает ученику ни в списке, ни в детали варианта;
- баллы и правильность скрыты до проверки учителем;
- нельзя выставить больше максимума за задание (422);
- чужой ученик не видит и не может сдать чужую попытку (404);
- другой учитель не видит вариант (404);
- банк заданий: темы из спецификации, правка ключа, запрет ключа на
  открытых заданиях, изоляция банка между учителями;
- дедупликация по источнику: один и тот же вопрос в двух вариантах —
  одна запись в банке, статистика объединяется.
