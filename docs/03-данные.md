# 03. Данные

27 таблиц и 12 перечислений в одной базе PostgreSQL 16. Схема описана в
`apps/api/src/db/schema.ts` через Drizzle; миграции лежат в
`apps/api/drizzle/` и нумеруются по порядку (сейчас 0000–0015).

## Главное правило

**Ограничения живут в базе, а не только в коде.** Приложение может ошибиться,
база — нет. Поэтому в схеме есть `CHECK`-ограничения, частичные уникальные
индексы и перечисления вместо свободных строк. Пример: доступ нельзя выдать
без срока действия, если он не пробный.

```sql
ALTER TABLE course_access ADD CONSTRAINT expiry_required_when_granted
  CHECK (access_granted = false OR expires_at IS NOT NULL OR is_trial = true);
```

## Персонал и арендаторы

`staff_users` — общая таблица учётных записей с ролью `owner | teacher |
assistant`. Способ входа зависит от роли, и это записано ограничением:
владелец входит по Telegram ID и не имеет пароля, преподаватель и помощник —
по логину и паролю и не имеют Telegram ID.

```sql
CHECK (
  (role = 'owner'     AND telegram_id IS NOT NULL AND username IS NULL AND password_hash IS NULL)
  OR (role IN ('teacher','assistant') AND telegram_id IS NULL AND username IS NOT NULL AND password_hash IS NOT NULL)
)
```

`teachers` — настройки преподавателя: порог штрафных баллов и язык
уведомлений. `assistants` привязывает помощника к преподавателю: эта связь и
есть арендатор. `assistant_course_permissions` задаёт права помощника по
каждому курсу отдельно.

`staff_notification_groups` — Telegram-группа, куда идут уведомления, одна на
преподавателя.

## Ученики и курсы

`students` — Telegram ID, имя, язык, телефон. Телефон записывается только из
контакта, которым ученик поделился о себе; вручную его ввести нельзя.

`courses` → `modules` → `lessons` → `lesson_materials` — дерево содержимого.
У урока есть тип (`live` или `recorded`), время, признак публикации и
`file_id` записи.

`homeworks` привязано к уроку, `homework_submissions` — к заданию и ученику,
с номером попытки, признаком опоздания и статусом.

`course_telegram_groups` — группа курса, куда приглашают учеников.

## Доступ, оплата, дисциплина

`course_access` — сердце допуска: выдан ли доступ, до какого числа, отозван ли,
пробный ли, когда начался пробный период, заморожен ли и когда удалён из
группы.

`course_applications` — анкета: ФИО, свой телефон, телефон родителей, пара
слов о себе. Одна анкета на пару (курс, ученик).

`course_penalty_points`, `course_blacklist`, `course_disciplinary_events` —
штрафные баллы, чёрный список и журнал всех дисциплинарных событий.

Идемпотентность автоматики держится на частичном уникальном индексе:

```sql
CREATE UNIQUE INDEX ... ON course_disciplinary_events (student_id, related_homework_id)
  WHERE event_type = 'missed_homework_deadline';
```

Задача о пропущенных работах может ходить по строкам сколько угодно раз —
второй штрафной балл за то же задание базa не примет.

## Бот и уведомления

`bot_pending_actions` — двухфазные действия бота: создано, взято
пользователем, использовано. Через них проходит прикрепление видео, сдача
работы, привязка групп, отправка фотографий по сертификатным заданиям.

`notifications_log` — журнал отправленного, с типом события, получателем,
каналом (`private_chat` или `group_chat`) и произвольной полезной нагрузкой в
JSONB. По нему же работает защита от повторов в периодических задачах.

## Сертификатный экзамен

`cert_exams` — вариант: файл, дедлайн, признак публикации.
`cert_items` — банк заданий, живущий отдельно от вариантов.
`cert_exam_items` — какое задание банка стоит на каком номере в каком варианте.
`cert_exam_attempts` и `cert_exam_answers` — попытки учеников и ответы, с
замороженным вердиктом по каждому закрытому заданию.

`cert_calibration_runs` и `cert_item_calibrations` — история калибровок по
Рашу: снимок на момент прогона, а не текущее значение. Видно, как трудность
уточняется с накоплением ответов.

## Перечисления

`staff_role`, `language`, `course_subject`, `lesson_type`,
`lesson_material_type`, `submission_status`, `disciplinary_event_type`,
`cert_exam_attempt_status`, `notification_recipient_type`,
`notification_channel`, `notification_type`, `bot_pending_action_type`.

Новое значение перечисления добавляется отдельным оператором в начале
миграции: Postgres не разрешает использовать только что добавленную метку в
той же транзакции, где она появилась.

## Миграции

`npm run db:migrate` прогоняет всё, чего ещё нет. Скрипт деплоя вызывает его
сам и считает ошибку фатальной — иначе новый код молча пойдёт по старой схеме.

Перед применением на боевой базе миграция проигрывается с нуля по всей цепочке
на отдельной базе. Это ловит то, чего не видно на своей машине: например,
использование новой метки перечисления в той же транзакции.
